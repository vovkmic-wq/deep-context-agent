# Промпт устранения дефектов evidence integrity (версия 0.6.0)

Ты — ведущий Python-инженер Deep Context Agent. Работай только в рамках
`TECHNICAL_SPEC.md` и `IMPLEMENTATION_PROMPT.md`. Цель — устранить три дефекта,
зафиксированные в ручном restart-тесте 2026-08-23, и довести локальный CLI до
проверяемого production-состояния.

## Исходные дефекты

1. Финальный текст LLM может сообщить иное число результатов, чем фактический
   `ToolMessage` и блок `Verified tool operations`.
2. Acceptance manifest проверяет имя, target, status, порядок и число вызовов,
   но не умеет доказать точное содержимое файла и минимальное число найденных
   записей.
3. После успешного запроса «вызови TOOL ровно один раз» модель может попытаться
   вызвать тот же TOOL повторно. Policy отклоняет повтор, но лишний model/tool
   цикл уже возник и нарушает контракт exact-once на уровне попыток.

## Обязательная реализация

1. Расширь безопасную запись audit структурированными полями
   `result_count` и `content_sha256`. Количество извлекай только из
   структурированного результата tool. SHA-256 вычисляй из фактических байтов
   файла внутри `AGENT_WORKSPACE` сразу после успешного `write_file`,
   `edit_file` или `read_file`; содержимое файла в audit не копируй.
2. Добавь acceptance manifest версии 2 с обратной совместимостью версии 1.
   Required event версии 2 может содержать `min_results` и
   `content_sha256`. Проверяй типы, диапазоны, допустимые tools и формат
   SHA-256 строго; неизвестные поля должны давать FAIL не через догадку LLM, а
   через ошибку parser. Forbidden events не должны ослабляться предикатами.
3. Для запроса точного количества результатов формируй пользовательский факт
   детерминированно из audit. Если LLM написала другое число, её утверждение о
   количестве не должно оставаться финальным источником истины. Для остальных
   count-bearing tools добавляй компактный авторитетный блок cardinality.
4. Распознавай явный контракт «TOOL ровно один раз» / «call TOOL exactly once».
   После первой фактической попытки исключай этот TOOL из следующего model
   request. Если provider всё же вернул устаревший повторный tool call, не
   исполняй его и заверши ответ на основании уже полученного evidence. Не
   ослабляй существующую защиту дубликатов для запросов без exact-once.
5. Обнови глобальный system prompt: ToolMessage и структурированный audit
   авторитетнее текста модели; exact-once означает одну фактическую попытку;
   после первого результата повтор запрещён; cardinality копируется буквально.
6. Обнови `TECHNICAL_SPEC.md`, `IMPLEMENTATION_PROMPT.md`, README,
   canonical acceptance prompt, историю версий и статус реализации. Подними
   версию пакета до 0.6.0.

## Обязательные тесты

1. Unit: parser принимает manifest v2 и отвергает неверные/несовместимые
   `min_results` и `content_sha256`; manifest v1 продолжает работать.
2. Unit: event проходит только при достаточном `result_count` и совпадающем
   `content_sha256`; несовпадение даёт первичный FAIL и BLOCKED для зависимых.
3. Integration: audit успешного чтения содержит SHA-256, но не тело файла.
4. Integration: при реальных четырёх результатах и ошибочном тексте модели
   пользователь получает авторитетное число 4.
5. Integration: модель, дважды возвращающая один и тот же `search_context` для
   запроса «ровно один раз», приводит ровно к одной фактической audit-записи;
   второй call не исполняется и не получает `denied` event.
6. Regression: root-delete, sentence-scoped запреты, cleanup completion gate,
   web verification, память и все прежние тесты остаются зелёными.
7. PowerShell: выполнить Ruff check, Ruff format check, полный pytest, package
   metadata, `pip check`, CLI help, `doctor`, `doctor --live`, затем отдельный
   restart-search с новым thread ID и machine-readable manifest v2,
   `min_results=1`, exact count 1.

## Критерий завершения

Работа завершена только когда все локальные и live-проверки успешны, restart
audit содержит ровно один `search_context`, `result_count >= 1`, финальная
cardinality совпадает с ToolMessage, секреты отсутствуют в diff, а проверенный
commit опубликован в существующий GitHub remote. При любом сбое исправь код и
повтори затронутый тест, затем весь обязательный контур.
