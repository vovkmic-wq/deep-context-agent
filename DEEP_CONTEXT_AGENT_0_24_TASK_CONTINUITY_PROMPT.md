# Этап 0.24: продолжение задач и проверяемое выполнение

Статус: реализовано в 0.24.0; результаты и ограничения — IMPLEMENTATION_STATUS.md.

1. Зафиксировать baseline и сохранить пользовательские изменения.
2. Ввести постоянную задачу в существующей SQLite: identity, thread, workspace,
   direct objective, workflow, scope, разрешение записи, этап, результат и revision.
   Логи/цитаты не создают задачу и не выдают разрешений. «Продолжи» разрешается
   через единственную подходящую задачу или явно выбранный task ID. Неоднозначность,
   смена workspace, отмена и завершение не дают произвольного resume.
3. Разделить точечное чтение, discovery и запись. Resume пересекает сохранённые
   права с текущими Ask/Plan/read-only/allow-write controls. Анализ лога — боковой
   ход, не замена цели. В каждый model step передавать актуальные runtime-права.
4. Сохранять каждую фактическую model attempt до/после исполнения в diagnostics,
   включая provider/model, prompt hash, duration, usage, finish/stop reason,
   retry и cancellation. Неизвестные показатели — null. Соблюдать redaction,
   retention, rollback isolation и запрет raw provider payload.
5. Ввести отдельно наблюдение повторов текста и контроль отсутствия tool progress.
   Детектор по умолчанию observe; enforce только явно. Не резать JSON/tool args,
   не принимать обрезанный код как завершённое изменение. Калибровать на прозе,
   коде и таблицах. Семантический повтор не выдавать за доказанный n-gram detector.
6. Ограничить model attempts/output/deadline. Повторы только для временных ошибок,
   с jitter/backoff. Не переисполнять graph/tools ради retry модели. Перед каждой
   моделью/инструментом проверять отмену и deadline. Для sync remote API не заявлять
   подтверждённое прекращение серверного inference после локальной отмены.
7. Сохранять active state отдельно от retrieval. Контекст содержит обязательную
   безопасность, текущий режим/права, цель и подтверждённые данные. Не увеличивать
   безусловно контекст или лимит шагов, не навязывать temperature=0 всем моделям.
8. Web terminal различает completed/partial/blocked/failed/cancelled. UI показывает
   активную задачу, её revision, область, фактическую модель и диагностический ID.
9. Регрессии: разработка → лог → продолжение; restart; неоднозначность; Ask после
   записи; revoked write; другой workspace; отмена; инструментальные циклы; текстовый
   повтор; легитимные code/JSON; сбой после mutation; concurrent claims; migrations.
10. Выполнить Ruff/pytest/types/build и изолированные live-проверки с существующим
    ключом и ограниченными бюджетами. Не менять пользовательский Ozon workspace.
11. Обновить глобальные документы и итоговый статус фактическими результатами.
    Не заявлять полную production-готовность, если обязательная проверка не выполнена.
12. В обоих выпадающих списках (чат и выбор/проверка провайдера) оставить не более
    пяти выбираемых chat-моделей, начиная с самых новых. Использовать release_date /
    released_at, если их возвращает провайдер; иначе явно подписать fallback на
    created (дата записи каталога, не релиз). Без дат не выдумывать хронологию.
    Исключать несовместимые типы моделей, сортировать до ограничения, не обрезать
    исходный каталог первыми 100 строками. Старую активную модель показывать как
    невыбираемый статус, не менять работающую задачу и настройки автоматически.
    Оставить полную backend-валидацию ранее выбранных доступных моделей.
    Подтверждённые даты официальных API-релизов дополняют метаданные каталога;
    alias и его датированный snapshot не занимают два места в пятёрке.
