# Промпт устранения ошибок полного acceptance и подготовки версии 0.5.0

Ты — ведущий Python-инженер по надёжности и безопасности LLM-агентов. Доведи
Deep Context Agent до production-ready версии 0.5.0, строго следуя
`TECHNICAL_SPEC.md` и фактическому runtime audit полного acceptance от
2026-08-23. Свободный текст LLM, её таблица и количество PASS не являются
доказательствами. После каждого раздела запускай целевые тесты, устраняй
первопричину каждого сбоя и повторно сверяй код, prompt и ТЗ.

## Подтверждённые проблемы 0.4.0

1. Строка «Не читай decoy.txt ... Проверь ... result.txt» запретила чтение обоих
   файлов: parser связал отрицательный глагол со всеми именами файлов строки,
   включая имя в следующем положительном предложении.
2. Из-за ложного запрета четыре требуемых чтения `result.txt` получили
   `denied`, включая post-delete проверку.
3. `write_todos` был вызван трижды вместо одного: служебный planning-tool имеет
   недетерминированное число обновлений и не должен входить в exact counts
   функционального acceptance.
4. После удаления root sentinel модель завершила ответ без обязательного
   `read_file -> error/not_found`, но в своей таблице заявила, что проверка была.
5. Один отсутствующий ранний ordered event породил длинную цепочку из зависимых
   FAIL, поэтому отчёт не отличал первичную ошибку от BLOCKED-проверок.
6. LLM сообщила о найденной записи памяти, хотя audit `search_context` вернул
   `0 result(s)`, и неверно посчитала общее число tool calls.
7. Restart-проверка памяти получила ложный `Runtime web verification: FAIL`:
   слово «текущее» в prose и служебное поле `"version"` внутри manifest вместе
   ошибочно классифицировались как запрос актуальной версии из сети.

## Обязательные изменения

### 1. Точная область отрицательной инструкции

- Разбирай каждое совпадение `do not/never read|open|show|display` и
  `не читай|не открывай|не показывай` только в пределах его текущего
  предложения/инструкционной части.
- Граница предложения определяется пунктуацией с последующим новым
  предложением; точка внутри имени `file.txt` границей не является.
- Запрещай все явно перечисленные пути/basename внутри отрицательной части, но
  не пути из следующего положительного предложения той же строки.
- Basename разрешено сопоставлять только с полными `/workspace/...` путями,
  явно присутствующими в текущем пользовательском запросе.
- Добавь регрессию на строку с `decoy.txt` и последующим положительным
  `result.txt`: запрещён только decoy, result читается успешно.

### 2. Недетерминированные служебные tools

- Расширь manifest версии 1 полем `allowed_unlisted_tools`: ограниченным списком
  известных tool names, вызовы которых отображаются в отчёте, но не требуют
  exact count и не считаются unexpected.
- Запрети пересечение `allowed_unlisted_tools` с `exact_tool_call_counts`,
  дубликаты, неизвестные tools и превышение лимитов.
- В каноническом acceptance укажи `write_todos` как allowed-unlisted и убери его
  exact count. В глобальном prompt потребуй не использовать `write_todos` для
  manifest-сценария: сам manifest уже является планом.
- Функциональные filesystem/runtime/context/web tools по-прежнему обязаны иметь
  exact counts; любой иной необъявленный tool остаётся FAIL.

### 3. Первичные FAIL и зависимые BLOCKED

- Если required event не найден при выполненной зависимости, регистрируй один
  первичный FAIL.
- Если его `after`-dependency не была найдена, помечай событие BLOCKED, а не
  новым независимым FAIL.
- Runtime verdict является PASS только при `FAIL=0` и `BLOCKED=0`.
- Отчёт обязан отдельно показывать PASS, FAIL, BLOCKED и PENDING, причины
  первичных ошибок и заблокированные зависимости.
- Ожидаемые `denied/error/not_found` остаются PASS только когда manifest явно
  разрешает их для конкретного event.

### 4. Обязательное завершение cleanup

- Раздели отрицательную инструкцию decoy и положительную проверку result на
  разные предложения/строки канонического prompt.
- Перед финальным ответом введи completion gate: последним функциональным tool
  call должен быть `read_file` точного sentinel после успешного `remove_path`.
- Модель не имеет права формировать таблицу до получения `error/not_found` этого
  чтения. Если доказательства нет, она должна продолжить tool loop.
- Runtime не должен полагаться только на дисциплину дешёвой модели. Если модель
  преждевременно вернула финальный текст или выбрала иной следующий call,
  manifest валиден, предыдущая
  `after`-dependency доказана и следующим пропущен безопасный postcondition
  `read_file -> error/not_found` либо явно запрошенный `remove_path -> success`,
  completion middleware заменяет финальный текст ровно одним таким tool call.
  Он не начинает root event, не превышает exact count, не читает запрещённый
  путь, не выходит из `/workspace/` и никогда не удаляет `/workspace/`. Для
  автоматического вызова target и разрешение мутации должны присутствовать в
  prose вне JSON manifest: один manifest не расширяет полномочия runtime.
- После того как модель сама успешно выполнила root event, runtime передаёт
  провайдеру `tool_choice` следующего dependency-ready event только если имя
  non-filesystem tool либо точный filesystem target и операция независимо
  разрешены prose, а exact count не исчерпан.
  Это предотвращает перестановку/лишние calls, но не генерирует содержимое
  записи и не начинает сценарий за модель.
- Для dependency-ready `read_file` runtime заменяет выбранный моделью target на
  точный prose-разрешённый target event и для положительного success-read, и для
  post-delete `error/not_found`; запрещённый путь никогда не подставляется.
- Для `remove_path` тем же образом фиксируются точный target и объявленный
  `recursive=true`; корень допустим только как явно ожидаемый denied-тест и
  остаётся защищён самим filesystem tool.
- Явное «не создавай/не изменяй/не удаляй» для пути имеет абсолютный приоритет:
  отрицательное предложение не может стать разрешением из-за manifest event или
  другой мутации в запросе; положительное намерение должно находиться рядом с
  точным prose-путём.
- Финальный ответ обязан использовать точные значения из ToolMessage: нулевой
  результат поиска нельзя описывать как найденную запись, а число calls нельзя
  угадывать. Программный audit остаётся авторитетным.

### 5. Тестирование и повторное исправление

- Unit: sentence-scoped forbidden-read parser, несколько запрещённых файлов,
  положительное имя следующего предложения и отсутствие ложного запрета.
- Unit: parser `allowed_unlisted_tools`, неизвестный tool, дубликат, пересечение
  с exact counts и корректное игнорирование `write_todos` в unexpected-check.
- Unit: один первичный missing event создаёт FAIL и зависимые BLOCKED без
  каскада независимых FAIL.
- Integration: `result.txt` читается, а decoy в том же составном запросе
  блокируется; содержимое decoy не раскрывается.
- Integration: преждевременные финальные ответы модели детерминированно
  преобразуются в последовательную цепочку `read missing -> remove sentinel ->
  read missing`; неверный следующий call заменяется ожидаемым postcondition, но
  middleware не начинает отсутствующий root event сам.
- Security integration: target, названный только внутри JSON manifest, не
  исполняется completion middleware и физически остаётся неизменным.
- Integration: после root event каждый model bind получает `tool_choice`
  следующего ordered event; лишнее чтение не может опередить создание decoy.
- Integration: правильный `read_file` с неправильным target заменяется точным
  положительно разрешённым target, а посторонний файл не читается.
- Contract: канонический prompt парсится и предусмотренный полный ordered audit
  даёт `FAIL=0`, `BLOCKED=0`, один PENDING.
- Web verification классифицирует только пользовательскую prose-часть:
  `<acceptance_manifest>` удаляется перед распознаванием текущей web-версии,
  цены или даты и не создаёт ложный FAIL для context search.
- Regression: root-delete, outside path, SSRF, PyPI, redaction, retry/rollback,
  persistent context и миллион строк продолжают проходить.
- Выполни Ruff lint, Ruff format check, полный pytest, editable package build,
  `pip check`, CLI help и безопасный doctor.
- Выполни полный изолированный PowerShell acceptance через существующий
  OpenAI-ключ и `gpt-5-nano`, с новыми workspace/data/thread. Не выводи ключ.
- При любом runtime FAIL или физическом несоответствии исправь первопричину и
  повтори автоматические и live-тесты до полного PASS.

### 6. Документация, версия и публикация

- Синхронизируй этот prompt, `IMPLEMENTATION_PROMPT.md`, глобальный prompt,
  `TECHNICAL_SPEC.md`, `README.md`, `IMPLEMENTATION_STATUS.md`, канонический
  `acceptance-prompt.txt` и `CHANGELOG.md`.
- Установи версию пакета и сетевые User-Agent `0.5.0`.
- После успешных тестов проверь staged diff на секреты, создай commit версии
  0.5.0 и отправь текущую ветку в настроенный GitHub remote.
- Не публикуй `.env.local`, базы, workspace или несвязанные пользовательские
  untracked-файлы.

## Условие завершения

Версия 0.5.0 считается production-ready только в заявленных границах локального
однопользовательского CLI и только если автоматические проверки проходят,
полный live acceptance имеет runtime verdict PASS, физический workspace
подтверждает cleanup, версия установлена, а опубликованный Git commit совпадает
с локальным HEAD. Для многопользовательского сетевого сервиса требуются
дополнительные изоляция, аутентификация и координация записей вне текущего ТЗ.
