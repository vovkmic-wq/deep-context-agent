# Промпт устранения дефектов acceptance и подготовки версии 0.3.0

Ты — ведущий Python-инженер и специалист по безопасности LLM-агентов. Доведи
Deep Context Agent до production-ready версии 0.3.0, опираясь на
`TECHNICAL_SPEC.md` и фактический ручной acceptance-лог от 2026-08-22. Не
считай свободный текст LLM доказательством выполнения. После каждого раздела
запускай относящиеся к нему тесты, исправляй причины сбоев и только затем
переходи дальше.

## Зафиксированные недостатки

1. Модель выдала несколько зависимых tool calls одновременно, из-за чего
   чтение, запись и удаление выполнились не в гарантированном порядке.
2. Одинаковая файловая мутация могла быть вызвана повторно в одном ходе.
3. Значение с явным маркером `DO_NOT_SHOW` попало в финальный ответ.
4. Модель сообщила об отказе открыть локальный URL без фактического результата
   web-tool текущего хода.
5. Для точной версии LangChain выполнялись повторные открытия одной страницы,
   но точное значение не было извлечено и проверено.
6. Удаление непустого явно указанного каталога завершилось ошибкой: модель
   удалила детей, но не повторила удаление самого каталога.
7. Таблица PASS/FAIL и число пройденных пунктов, сформированные самой LLM,
   противоречили фактическому audit.
8. Команда `/paste ТЕКСТ` не включала текст после `/paste` в многострочный
   запрос и могла снова приводить к фрагментации ручного теста.

## Обязательные изменения

### 1. Последовательность и идемпотентность tools

- На каждом model call передавай `parallel_tool_calls=false`.
- На уровне middleware независимо от поведения провайдера пропускай не более
  одного tool call из одного ответа модели. Остальные вызовы не исполняй:
  следующий шаг модели должен увидеть результат первого tool и заново решить,
  какое действие требуется.
- В пределах одного пользовательского хода отклоняй повторный идентичный вызов
  mutating-tool (`write_file`, `edit_file`, `make_directory`, `remove_path`).
- Сброс счётчика выполняй перед каждым новым `AgentRuntime.ask`.
- Все отклонения должны попадать в программный audit со статусом `denied`.

### 2. Безопасность содержимого и audit

- Найди в исходном запросе атомарные значения с маркером `DO_NOT_SHOW` или
  `НЕ_ПОКАЗЫВАТЬ` и замени их в финальном ответе и audit на `[REDACTED]`.
- Не изменяй содержимое файлов: редактирование применяется только к выводу и
  архивируемому assistant-ответу.
- Audit не должен содержать тело файла, веб-страницы, API-ключ, абсолютный
  физический путь workspace или пользовательский секрет.
- Для `read_context_window` фиксируй число результатов, для удаления каталога —
  безопасный признак `recursive=true`, не раскрывая лишние аргументы.

### 3. Детерминированная веб-проверка

- Сохрани `web_search` и защищённый `fetch_web_page` с запретом private/local IP,
  нестандартных портов, credentials и небезопасных redirect.
- Если пользователь передал точный URL и просит его открыть, агент обязан
  вызвать `fetch_web_page`; предположение модели об отказе не является
  доказательством.
- Добавь узкий tool `get_pypi_package_info`, который получает официальный
  `https://pypi.org/pypi/<package>/json`, проверяет публичный адрес, ограничивает
  размер/timeout и возвращает только package, version, project URL и UTC
  `checked_at`.
- Текущая версия пакета считается проверенной при успешном
  `get_pypi_package_info` либо успешном `fetch_web_page` официального источника
  текущего хода. Ошибка должна быть структурированной и не подменяться старым
  retrieval.

### 4. Удаление каталогов

- Корень `/workspace/` всегда запрещён, включая удаление потомков вместо корня.
- Для явно запрошенного удаления конкретного подкаталога используй один
  `remove_path(path, recursive=true)`. Не перечисляй и не удаляй его детей по
  одному, если пользователь запросил удаление каталога целиком.
- Ошибка непустого каталога должна быть безопасной и объяснять допустимый
  повтор с `recursive=true`, без физического Windows-пути.

### 5. Ввод и достоверность финального статуса

- Поддержи `/paste` и `/paste ПЕРВАЯ_СТРОКА`; оба режима завершаются `/end` и
  образуют ровно один пользовательский turn.
- Любая LLM-самооценка `CANDIDATE_RESULT`, `OVERALL PASS/FAIL` или «общий итог»
  помечается программно: при non-success audit — `FAIL`, без внешней проверки —
  `NOT_VERIFIED`. Она не может присвоить проекту production-ready статус.
- Источником итогового статуса являются Ruff, pytest, CLI smoke, изолированный
  live-smoke и фактический audit.

### 6. Тесты

- Unit: принудительный `parallel_tool_calls=false`, обрезка параллельных
  tool calls, запрет идентичной мутации, сброс между turns.
- Unit: редактирование `DO_NOT_SHOW` в ответе и audit без изменения файла.
- Unit: PyPI JSON success/error/limit и private URL rejection без реальной сети.
- Integration: зависимые write/read/edit/delete выполняются последовательно;
  root-delete не меняет sentinel; конкретный непустой каталог удаляется одним
  recursive call.
- CLI: `/paste`, `/paste ПЕРВАЯ_СТРОКА`, `/cancel`, `ask --file`, stdin.
- Regression: локальный URL не получает сетевой доступ; точный путь не приводит
  к чтению посторонних файлов; внешний путь не создаёт placeholder.
- Запусти `ruff check --no-cache .`, `ruff format --check --no-cache .`, полный
  `pytest -ra`, CLI help и `doctor`.
- Выполни один минимальный live-smoke через существующий OpenAI-ключ в новых
  уникальных `AGENT_WORKSPACE`, `AGENT_DATA_DIR` и thread ID. Не выводи ключ.

## Условие завершения

Версия 0.3.0 считается production-ready только когда все автоматические
проверки проходят, planned symlink skip явно объяснён, live-smoke успешен либо
зафиксирована внешняя причина его невозможности, а повторная сверка каждого
пункта этого промпта и критериев ТЗ не выявляет неподтверждённых заявлений.
