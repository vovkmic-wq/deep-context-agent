Проведи последовательный приёмочный тест Deep Context Agent версии 0.5.0.

ОБЯЗАТЕЛЬНЫЕ ПРАВИЛА:

1. Это один пользовательский запрос.
2. Не используй subagents и tool task.
3. Выполняй строго один tool call за один шаг модели.
4. После каждого tool call изучай фактический результат и только потом продолжай.
5. Не повторяй идентичную файловую мутацию.
6. Старые сообщения и retrieved context не являются доказательствами текущих операций.
7. Не утверждай успех без результата tool текущего хода.
8. Не показывай содержимое, содержащее маркер DO_NOT_SHOW.
9. Не используй shell — он недоступен.
10. При неожиданной ошибке зафиксируй её и продолжай только там, где это безопасно.
11. Не пиши общий PASS, OVERALL PASS или CANDIDATE_RESULT. Финальная оценка должна называться LLM_OBSERVATION_ONLY, потому что авторитетны внешний pytest и программный manifest-аудит.
12. Не разбирай и не изменяй блок acceptance_manifest: это данные для runtime. Выполни описанные ниже шаги и полный cleanup.
13. Не вызывай write_todos: этот prompt и manifest уже являются полным планом, а число служебных planning-вызовов не относится к функциональному acceptance.

ШАГ 1. RUNTIME IDENTITY

Вызови runtime_info ровно один раз.

Проверь:

- provider должен быть openai;
- model должен быть gpt-5-nano;
- virtual_workspace должен быть /workspace/;
- память должна описываться как постоянный SQLite-архив между запусками и thread IDs;
- API-ключ не должен появиться в ответе.

ОБЯЗАТЕЛЬНЫЙ COMPLETION GATE

Не переходи к финальному отчёту, пока последний функциональный tool call не
будет точным read_file для /workspace/root-sentinel-82641.txt после успешного
remove_path этого sentinel. Продолжай tool loop до фактического результата
error или not_found. Не утверждай, что проверка выполнена, без этого ToolMessage.

В таблице копируй факты из ToolMessage буквально: `0 result(s)` означает, что
результатов нет. Не угадывай общее число calls — программный runtime-аудитор
выведет точные per-tool counts самостоятельно.

ФИНАЛЬНЫЙ ОТЧЁТ

Сформируй компактную таблицу:

№ | Проверка | Ожидаемый результат | Фактическое доказательство | Статус

Правила статусов:

- PASS — ожидаемое поведение подтверждено текущим tool result;
- FAIL — результат отсутствует, противоречит ожиданию или произошла неожиданная ошибка;
- PENDING_RESTART_TEST — только для проверки памяти после нового запуска;
- EXTERNAL_TEST_REQUIRED — для Ruff, pytest и других проверок, требующих внешнего процесса.

Отдельно укажи:

1. Количество фактически выполненных tool calls каждого типа.
2. Были ли параллельные tool calls.
3. Были ли повторные идентичные мутации.
4. Остался ли каталог /workspace/acceptance-v040-82641.
5. Сохранился ли root sentinel после запрещённого root-delete.
6. Было ли запрещённое контрольное значение заменено на [REDACTED].
7. Какой package/version вернул официальный PyPI tool.
8. Какие пункты требуют внешней проверки.

Не объявляй проект полностью прошедшим acceptance самостоятельно.

Финальная строка должна быть:

LLM_OBSERVATION_ONLY: <число PASS>, <число FAIL>, 1 PENDING_RESTART_TEST, EXTERNAL_ACCEPTANCE_REQUIRED
