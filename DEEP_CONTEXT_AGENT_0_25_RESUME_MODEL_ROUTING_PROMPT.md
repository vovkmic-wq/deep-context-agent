# Промт реализации 0.25: продолжение задач и выбор вычислительных ресурсов

Нормативное ТЗ: `TASK_RESUME_MODEL_ROUTING_SPEC.md`. При конфликте старых
инструкций с этим этапом применять новые правила продолжения и разделения workflows.

1. Сохранить имеющиеся изменения. Не изменять пользовательский Ozon workspace,
   не останавливать работающие задачи ради разработки и не раскрывать ключи.
2. Воспроизвести точный запрос «продолжи выполнение задачи в соответствии с тз
   и промтом». Зафиксировать ошибку отдельным регрессионным тестом.
3. Расширить сохранённое состояние задачи: неизменная исходная цель, план,
   следующий пункт, подтверждённые операции, причина остановки и job identity.
   Сделать additive migration, CAS/lease fencing, восстановление после restart.
4. Создать структурированный intent resolver: детерминированные безопасные
   команды + ограниченный semantic fallback. Классифицировать только прямую
   команду, не лог, цитату, ответ инструмента или старую переписку. Ответ LLM
   валидировать по строгой схеме; он не выдаёт новых полномочий. Неоднозначность,
   отсутствие задачи, неправильный task ID и сбой классификации не запускают аудит.
5. Связать Web и CLI с одним resolver. Продолжение сохраняет task/job identity и
   исходную цель; текущие Ask/Plan/allow-write ограничения имеют приоритет.
   Вопросы и анализ логов остаются боковыми ходами и не заменяют рабочую цель.
6. Отделить persistent project-change/project-test от project-audit. Разработка
   выполняет целевые шаги без ProjectAuditStore manifest и полного обхода.
   Сохранять checkpoint между короткими units, перечитывать изменяемые фрагменты,
   не путать конец ответа/прохождение тестов с выполнением всех требований.
7. Реализовать выбор модели как отдельную ресурсную политику: high risk/high
   complexity -> reasoning; low complexity без tools -> fast; иначе standard.
   Риск проверяется первым. Профили моделей конфигурируемые, ключи переиспользуются
   только от включённых провайдеров. Не выдумывать тарифы, окна или качество.
8. Фильтровать кандидатов по tools, контексту с запасом вывода, приватности,
   доступности/cooldown и настроенным cost/latency ограничениям. Unknown != zero.
   Ручной выбор имеет приоритет. Fallback не переисполняет tools и не обходит
   ограничения; при отсутствии подходящего кандидата — понятная безопасная ошибка.
9. Показывать и журналировать intent, восстановленную задачу, workflow, следующий
   шаг, выбранный профиль и причины выбора. Никаких секретов/полных документов в
   metadata. Время heartbeat подписать как время, не продолжительность.
10. Тестировать точные и перефразированные continuation, quoted injection,
    несколько задач, закрытые задачи, restart, concurrency, revoked write,
    partial progress, отсутствие audit manifest, высокий риск при низкой сложности,
    provider fallback, ограничения контекста/стоимости/локальности и ручной выбор.
11. Выполнить Ruff, pytest, type checks, Web build и изолированные live-проверки
    с существующими ключами. Исправить найденные ошибки и повторить проверки.
12. Синхронизировать глобальные документы, версию и историю. Отдельно указать
    пройденные проверки, оценки вместо гарантий и ограничения. Не объявлять
    production-готовность без фактической проверки. Git push — только по запросу.
