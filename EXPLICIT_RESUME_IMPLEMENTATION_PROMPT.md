# Промт исправления продолжения

Следуй EXPLICIT_RESUME_TECHNICAL_SPEC.md и действующим ограничениям проекта.

1. Воспроизведи отказ продолжения; зафиксируй регрессионные тесты без LLM.
2. Реализуй типизированное действие, минуя classifier, сохранив CAS/lease/scope.
3. Реализуй VERIFY-only и безопасную связь новой проверки с источником.
4. Добавь восстановление по доказательствам, без повторения неизвестных записей.
5. Журналируй отклонённые действия до создания model turn.
6. Добавь кнопки UI и runtime-owned статус, защиту от повторного запуска.
7. Проведи автоматические и изолированные live-тесты; исправь ошибки.
8. Обнови отчёт приёмки, затем опубликуй проверенные изменения в Git.

## Блок A — контракт и защита
Проверь действующие task/job identity и разрешения. Реализуй action DTO, проверку
CAS и lease, долговечный reservation. Ни одна строка пользовательского лога не
должна попасть в источники полномочий. Зафиксируй A01–A04 тестами.

## Блок B — безопасное восстановление
Не снимай reconciliation_required вручную. Добавь ограниченный отчёт сверки,
затем явное создание связанной проверки с выбранным корнем и новой identity.
Проверь неизменность исходной задачи и отсутствие повторных мутаций (A05–A07).
Регрессионно проверь legacy verification flags и quoted путь с пробелами при
одновременном наличии родительского manifest. Ask/Plan не должны менять режим
или захватывать lease через совместимый API явного действия.

## Блок C — интерфейс и журнал
Используй одни сервисы для кнопок и API; не дублируй маршрутизацию в JS.
Сохрани action key при повторе и понятную причину отказа. Не стирай текст,
который пользователь ещё не отправил. Покажи pending без ложного «запущено».
Статус задачи берётся из runtime, а не из переписки (A09–A10).

## Блок D — проверка и выпуск
Запусти Ruff, pytest, mypy, compileall, frontend build/tests. Отдельно выполни
реальный HTTP прогон на свободном loopback-порту с изолированными БД/venv:
unknown link → reconcile → linked VERIFY FAIL → approved REPAIR → VERIFY PASS.
Повтори проверки после обнаруженного дефекта; приложи безопасные IDs и итоговые
коды команд. Не публикуй реальные журналы с пользовательскими данными.
Проверь визуально новые действия в браузере, затем обнови статус и CHANGELOG.

Не меняй действующие пользовательские задачи и не снимай защитные блокировки
ради зелёного результата. Не утверждай завершение непроверенных пунктов.
