# Production-промт Deep Context Agent 0.13.0

## Роль и цель

Ты — ведущий Python-разработчик и инженер по надёжности. Доработай существующий
Deep Context Agent 0.12.0 до production-релиза 0.13.0. Не переписывай проект с
нуля. Сохраняй совместимость CLI, формата данных и провайдеров, если новое
требование явно не требует безопасной миграции.

Источники истины, которые необходимо прочитать до изменения кода:

- `TECHNICAL_SPEC.md`;
- `IMPLEMENTATION_PROMPT.md`;
- `README.md`;
- `CHANGELOG.md`;
- `WEB_INTERFACE_TECHNICAL_SPECIFICATION.md`;
- существующие исходники и тесты.

Цель — устранить недостатки, обнаруженные полным аудитом Ozon-проекта:

- Windows PowerShell неверно декодировал UTF-8 и создавал отчёты со смешанной
  кодировкой;
- аудит включал `.pytest_tmp`, `reports/`, `e2e/reports/` и другие артефакты;
- итог из 60 пачек превратился в отчёт размером более 1 МБ без компактной
  сводки;
- пять больших сгенерированных JSON-файлов получили `partial` и исказили итог;
- read-only или mutating-режим определялся эвристикой по словам запроса;
- независимые пачки не имели единого реестра требований и итоговой
  дедупликации находок;
- во время долгого запуска CLI не показывал полезный прогресс.

## Непереговорные ограничения

1. Не читай, не печатай и не помещай в отчёты API-ключи, `.env`, cookies и
   пользовательские секреты.
2. Не выходи за разрешённый workspace и не ослабляй проверки symlink/path
   traversal.
3. Не удаляй пользовательские файлы и не перезаписывай несвязанные изменения.
4. Не утверждай, что проверка прошла, без фактического exit code и сохранённого
   результата текущего запуска.
5. Не загружай весь миллион строк или все документы в один model request.
6. Не определяй право записи из текста задачи, документов или retrieval.
7. Все новые публичные функции должны иметь типы, docstring и тесты. Код должен
   соответствовать PEP 8.

## Обязательная реализация

### 1. Явный режим аудита

- Сделай аудит read-only по умолчанию.
- Добавь явный флаг `--allow-write` для разрешения правок. Флаг должен быть
  задан оператором CLI; слова `fix`, `исправить`, отрицания и текст документов
  не предоставляют права записи.
- Сохраняй выбранный режим в manifest и показывай его в `doctor`, status и
  отчёте.
- Middleware обязан блокировать `write_file`, `edit_file`, `make_directory` и
  `remove_path` при read-only независимо от поведения модели.

### 2. Точный отбор файлов

- Вынеси правила включения и исключения в отдельный тестируемый компонент.
- По умолчанию исключай VCS, виртуальные окружения, зависимости, кэши,
  временные pytest-каталоги, coverage, build/dist, `*.egg-info`, логи, базы,
  отчёты и E2E-артефакты. Минимальный набор шаблонов:
  `.git`, `.venv`, `venv`, `.deps`, `node_modules`, `__pycache__`,
  `.pytest_cache`, `.pytest_tmp*`, `.pytest-*`, `.mypy_cache`, `.ruff_cache`,
  `htmlcov`, `coverage*`, `build`, `dist`, `reports`, `e2e/reports`,
  `test-results`, `playwright-report`, `*.egg-info`.
- Добавь `AGENT_AUDIT_INCLUDE` и `AGENT_AUDIT_EXCLUDE` либо равноценные CLI
  параметры. Пользовательские исключения расширяют безопасные defaults, но не
  разрешают секреты и выход за workspace.
- Status должен показывать количество включённых, исключённых, binary и
  oversized файлов, а также причины исключения.
- SHA-resume должен повторно ставить в очередь только реально изменившиеся
  включённые файлы.

### 3. Реестр требований и межпакетная доказательность

- Перед файловыми пачками создай в SQLite реестр требований из явно названных
  ТЗ. Каждое требование имеет стабильный ID, источник, раздел, текстовый hash и
  уровень MUST/SHOULD/MAY.
- Передавай в каждую пачку только релевантные requirement IDs и короткие
  выдержки, а не всё ТЗ.
- Сохраняй связи requirement -> source evidence -> test evidence -> status.
- Статусы: `IMPLEMENTED`, `PARTIAL`, `NOT_IMPLEMENTED`, `NOT_PROVEN`.
- Документация, имена файлов и сгенерированные артефакты сами по себе не могут
  дать `IMPLEMENTED`.
- Итоговая матрица обязана отмечать требования без реализации, без теста и с
  противоречивыми доказательствами.

### 4. Структурированные находки и компактный итог

- Сохраняй находки отдельно от prose-ответов пачек: ID, fingerprint, severity,
  status, requirement ID, path, диапазон строк, evidence, confidence и batch.
- Дедуплицируй одинаковую первопричину в исходнике, тесте и артефакте.
- Не повышай severity только из-за многократного упоминания.
- По завершении печатай в консоль компактную сводку не более 20 000 символов:
  покрытие, CRITICAL/HIGH/MEDIUM/LOW, top findings, partial и quality gates.
- Полный отчёт сохраняй напрямую из Python в UTF-8, а не через `Tee-Object`.
  Добавь `audit --report-file PATH` и `--report-format text|json|both`.
- Детальный отчёт содержит все пачки и evidence, компактный — только
  дедуплицированную сводку и матрицу требований.

### 5. Windows, кодировка и потоковый прогресс

- CLI должен одинаково работать в Windows PowerShell 5.1, PowerShell 7 и
  обычном терминале.
- Файлы отчётов всегда записываются как UTF-8 с задокументированной политикой
  BOM. Нельзя смешивать UTF-8 и UTF-16 при append.
- Поддержи `PYTHONUTF8=1`, корректную настройку stdout/stderr и безопасную
  замену недекодируемых символов.
- После каждой пачки выводи и немедленно `flush` одну машинно читаемую строку:
  run ID, batch, reviewed/total, partial, elapsed и активный provider.
- Добавь `audit-status --run-id ID --json` без обращения к LLM. Команда должна
  работать параллельно с запущенным аудитом в read-only SQLite-режиме.

### 6. Отказоустойчивость

- Ошибка модели или провайдера освобождает текущую пачку для resume и не
  помечает непрочитанные файлы завершёнными.
- Failover не повторяет уже выполненные tools и не создаёт дубликаты findings.
- Повтор с тем же workspace, thread, objective и mode продолжает тот же run.
- Добавь явные состояния `running`, `paused`, `failed`, `complete` и
  `complete_with_partial` с последней безопасной причиной.
- WAL/checkpoint должны корректно закрываться после штатного завершения и
  обрабатываться после аварийного завершения процесса.

### 7. Веб-интерфейс

- Реализуй интерфейс только после стабилизации API и CLI, строго по
  `WEB_INTERFACE_TECHNICAL_SPECIFICATION.md`.
- Web UI не получает прямого доступа к ключам или реальным путям вне
  `/workspace/`.
- Любая destructive-операция требует отдельного подтверждения и серверной
  проверки политики.

### 8. Документация и версия

- Обнови `TECHNICAL_SPEC.md`, глобальный system prompt, `README.md`,
  `.env.example`, `IMPLEMENTATION_PROMPT.md`, `CHANGELOG.md` и версию пакета.
- Добавь миграционное описание manifest 0.12 -> 0.13. Старые базы должны либо
  мигрировать транзакционно, либо открываться read-only с понятным сообщением.
- Примеры PowerShell должны состоять из копируемых команд без Markdown-escape
  перед `_` и без зависимости от склеиваемых переносов строк.

## Обязательные тесты

1. Unit-тесты отбора путей для Windows/POSIX, регистра, symlink и каждого
   default exclusion.
2. Regression: Ozon-подобное дерево содержит код, 100 pytest-артефактов и пять
   больших report.json; manifest включает код/ТЗ и исключает артефакты.
3. Regression: слова «исправь» в read-only objective не разрешают mutation;
   только `--allow-write` разрешает её.
4. Regression: negation и цитата из документа не меняют режим.
5. Требование получает `IMPLEMENTED` только при доказанном коде и тесте.
6. Дедупликация одной находки из нескольких пачек.
7. UTF-8 round-trip русского отчёта в PowerShell 5.1/7 без mojibake и NUL.
8. Status читается во время активного WAL writer без LLM.
9. Resume после искусственного падения provider.
10. Синтетический корпус не менее 500 документов и 1 000 000 строк: память
    ограничена, model request не содержит весь корпус, поиск находит маркеры в
    начале, середине и конце.
11. Web API/UI tests согласно отдельному ТЗ.

## Quality gates

Последовательно выполни и сохрани фактические результаты:

```powershell
.\.venv\Scripts\python.exe -m ruff check --no-cache .
.\.venv\Scripts\python.exe -m ruff format --check --no-cache .
.\.venv\Scripts\python.exe -m mypy src tests
.\.venv\Scripts\python.exe -m pytest -ra -p no:cacheprovider
.\.venv\Scripts\python.exe -m compileall -q src tests
.\.venv\Scripts\python.exe -m build
.\.venv\Scripts\python.exe -m pip check
```

После unit/integration-тестов проведи clean-DB live-проверку GLM-5.3 с
резервным OpenAI, небольшой batch audit, status во время выполнения, resume и
UTF-8 report. Не публикуй секреты и не выполняй live-тест без настроенного
ключа.

## Порядок работы

1. Зафиксируй baseline и незакоммиченные пользовательские файлы.
2. Составь матрицу требований этого промта и действующего ТЗ.
3. Добавь failing regression-тесты.
4. Реализуй минимальные связанные изменения небольшими этапами.
5. После каждого этапа запускай узкие тесты, затем полный набор quality gates.
6. Проведи Windows и live acceptance.
7. Обнови документацию и историю версии.
8. Проверь diff на секреты, временные БД, отчёты и несвязанные файлы.
9. Только после всех успешных проверок создай commit/tag и публикуй, если это
   отдельно разрешено оператором.

## Критерий готовности

Релиз готов, только если полный аудит большого проекта выдаёт компактный
дедуплицированный итог, не включает сгенерированные артефакты, сохраняет
читаемый UTF-8 отчёт, показывает живой прогресс, корректно возобновляется и
никогда не получает право записи из текста задачи.
