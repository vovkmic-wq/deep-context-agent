# Промпт устранения дефектов полного acceptance и подготовки версии 0.4.0

Ты — ведущий Python-инженер и специалист по надёжности LLM-агентов. Доведи
Deep Context Agent до production-ready версии 0.4.0 по `TECHNICAL_SPEC.md` и
фактическому ручному acceptance-аудиту от 2026-08-22. Свободный текст модели не
является доказательством. После каждого раздела запускай целевые тесты,
устраняй первопричину каждого сбоя и заново сверяй результат с ТЗ.

## Зафиксированные недостатки 0.3.0

1. В одном ходе повторно вызывались `fetch_web_page`,
   `get_pypi_package_info` и `list_context_sources` с идентичными аргументами.
2. `result.txt` читался пять раз, хотя сценарий не требовал лишних чтений.
3. Модель прочитала `decoy.txt` вопреки прямому запрету «не читай».
4. После удаления тестового каталога не было ordered-доказательства
   `read_file(result.txt) -> error/not_found`.
5. Root sentinel не был удалён отдельным `remove_path`, и после удаления не было
   подтверждения отсутствия.
6. Модель заявила, что sentinel удалён, хотя физическая проверка показала его
   существование.
7. Финальный ответ не содержал требуемых фактических количеств вызовов каждого
   tool и выдал ошибочную самооценку `1 PASS, 0 FAIL`.
8. Старый runtime guard считал любой `denied/error/not_found` провалом, хотя для
   root-delete, private URL и post-delete read это ожидаемые результаты.

## Обязательные изменения

### 1. Политика вызовов tools

- Сохрани `parallel_tool_calls=false` и не более одного tool call на model step.
- Отклоняй повтор идентичной мутации в текущем turn.
- Отклоняй повтор идентичного runtime/context/listing/web-вызова в текущем
  turn; первая фактическая ошибка тоже считается завершённым вызовом и не
  должна провоцировать повтор.
- Для `read_file` веди счётчик по нормализованному пути и версии его состояния.
  Разрешай не более двух чтений неизменённого пути. Успешные write/edit/remove
  этого пути, а также recursive remove его родителя, создают новую версию.
- Все policy-отказы возвращай как `ToolMessage` со статусом `denied` и включай
  в текущий программный audit.
- Сбрасывай все per-turn ledger перед каждым `AgentRuntime.ask`.

### 2. Явный запрет чтения

- Разбирай строки с `do not/never read|open|show` и
  `не читай|не открывай|не показывай`.
- Если в запрете дан basename, сопоставляй его только с полными путями
  `/workspace/...`, явно упомянутыми в том же пользовательском запросе.
- Проверяй запрет до filesystem tool. Упоминание пути в другой части составного
  prompt не отменяет запрет.
- Не раскрывай содержимое запрещённого файла в ответе, audit или архиве.

### 3. Машиночитаемый acceptance manifest

- Поддержи ровно один ограниченный JSON-блок
  `<acceptance_manifest>...</acceptance_manifest>` версии 1.
- Разреши только известные tools, допустимые статусы, точные количества,
  required events, forbidden events, зависимости `after` и список внешних
  pending-проверок. Ограничь размер и число элементов.
- Считай каждый фактический tool attempt, включая policy-denied.
- Считай вызов tool без объявленного exact count ошибкой manifest-сценария.
- Сверяй required events с audit последовательно; одно событие audit не может
  удовлетворять два требования. `after` обязан ссылаться на ранее найденное
  required event.
- Ожидаемые `denied`, `error` и `not_found` являются PASS, если manifest явно
  допускает такой статус.
- Forbidden event является FAIL при любом совпавшем фактическом вызове,
  включая `denied`: сценарий не должен был вызывать tool вообще.
- После ответа LLM программно добавляй per-tool counts, counts по статусам,
  число PASS/FAIL/PENDING, причины каждого FAIL и итоговый runtime verdict.
- При отсутствии manifest любая самооценка `CANDIDATE_RESULT`,
  `LLM_OBSERVATION_ONLY`, overall/общий PASS остаётся `NOT_VERIFIED`, а не
  вычисляется по принципу «все статусы success».

### 4. Полнота сценария и cleanup

- Канонический acceptance prompt должен требовать точные количества tools,
  запрещать чтение decoy и содержать ordered events для всех стадий.
- Обязательно проверить результат после удаления тестового каталога.
- Root-delete должен дать `denied`, после чего sentinel читается успешно.
- Затем sentinel удаляется отдельным точным вызовом и его отсутствие
  подтверждается новым чтением `error/not_found`.
- Проверка памяти после рестарта остаётся `PENDING_RESTART_TEST` и выполняется
  отдельным процессом с тем же `AGENT_DATA_DIR` и новым thread ID.

### 5. Документация и версия

- Синхронизируй этот промпт, `IMPLEMENTATION_PROMPT.md`, глобальный prompt,
  `TECHNICAL_SPEC.md`, `README.md`, `IMPLEMENTATION_STATUS.md` и `CHANGELOG.md`.
- Укажи, что manifest-аудитор оценивает текущий turn, а pytest остаётся внешним
  источником качества кода.
- Синхронно установи версию пакета и сетевые User-Agent `0.4.0`.
- Не добавляй shell execution и не расширяй доступ за `AGENT_WORKSPACE`.

### 6. Обязательные тесты

- Unit: строгий parser manifest, неизвестные поля/tools/status, размер и
  зависимости.
- Unit: exact counts, ordered required events, forbidden events, ожидаемые
  negative statuses, per-tool/status report и ложный LLM verdict.
- Integration: повторные runtime/PyPI/context calls получают `denied`.
- Integration: третье чтение неизменённого пути получает `denied`, а ledger
  сбрасывается между turns.
- Integration: попытка `read_file` для явно запрещённого decoy блокируется и не
  раскрывает маркер.
- Regression: root-delete, recursive cleanup, post-delete reads, внешний путь,
  SSRF, redaction, retry/rollback и большой контекст продолжают работать.
- Выполни Ruff lint, Ruff format check, полный `pytest -ra`, CLI help и doctor.
- Один минимальный live-smoke разрешён только с существующим ключом, новыми
  уникальными workspace/data/thread, без вывода секрета и без полного дорогого
  acceptance-сценария.

## Условие завершения

Версия 0.4.0 считается production-ready в заявленных границах локального
однопользовательского CLI, только если все автоматические проверки прошли,
planned symlink skip объяснён, live-smoke успешен или документирована внешняя
причина, а повторная сверка кода и документации с каждым пунктом этого промпта и
ТЗ не выявляет неподтверждённых утверждений.
